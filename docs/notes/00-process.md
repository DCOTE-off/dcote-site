# Цикл разработки

## Проблема, которую решаем

Симптом: садишься за одну задачу, по дороге замечаешь три других, правишь их,
в конце в `git status` двадцать файлов и непонятно, что писать в сообщение.

Это видно в истории: `494e937` — 70 файлов, `fabec55` — 47 файлов,
`b557f32` — 43 файла. Названия при этом обобщённые («harden content and
integrations»), потому что одним словом такой объём не описать.

Это не проблема дисциплины. Это попытка делать две несовместимые вещи
одновременно: исследовать и оформлять. Их надо разнести по времени.

## Срочно: небезопасная настройка ветки

Ветка `comments` отслеживает `origin/production`, а `deploy.yml` триггерится
на push в `production`. То есть `git push` без аргументов с этой ветки
задеплоит незаконченную работу в прод.

```bash
git branch --unset-upstream
git branch -m comments inertia-home
```

Дополнительно стоит поставить локальную защиту от прямого пуша в прод:

```bash
git config --global push.default current
```

## Правило разделения коммитов

Один коммит — это одно изменение, которое можно откатить в одиночку, и сайт
останется рабочим. Не «один файл», не «один час работы». Единица откатываемости.

Тест на название: если в сообщение хочется вставить «и» — это два коммита.
«Поправил метрики и подключил шрифты» → два коммита. Работает почти всегда.

Частота: каждые 30-90 минут или на каждом «оно заработало». Если файлов больше
десяти и это не миграция и не переименование, значит надо было раньше.

## Техника: грязный процесс, чистый результат

Ты solo на своих ветках, поэтому историю можно переписывать. Работай как удобно,
коммить мусор:

```bash
git commit -am wip
git commit -am wip
```

В конце сессии разложи:

```bash
git reset --soft HEAD~3   # вернуть изменения в индекс, файлы не тронуты
git add -p                # раскладывать по кускам
```

`git add -p` — главный инструмент для этой проблемы. Показывает изменения
ханками и спрашивает по каждому: брать или нет. Позволяет собрать коммит из
части файла, а не из файла целиком. Именно это решает «поправил стили заодно».

Клавиши в `add -p`: `y` взять, `n` пропустить, `s` разбить ханк мельче,
`e` редактировать вручную, `q` выйти.

## Техника: скрэтч-файл для отвлечений

Завести `NOTES.md` в корне, добавить в `.gitignore`.

Когда по дороге замечаешь «а тут стили косые» — не правишь, а пишешь строку и
возвращаешься к задаче. Даже если правка на 10 секунд: 10 секунд превращаются
в час, это и есть механизм расползания.

Раз в неделю разгребаешь накопленный список отдельной сессией. Получаются
чистые мелкие коммиты, каждый по своей теме.

Если всё-таки увело в сторону: `git stash` перед прыжком, либо доделай и потом
раздели через `add -p`. Второе честнее для того, как ты реально работаешь.

## Формат сообщений

Conventional Commits уже используется — это хорошо. Одна правка: скоупы делать
узкими. Не `feat(site)`, а `feat(comments)`, `fix(header)`, `perf(anime)`.
Скоуп `site` означает «не смог определить, что именно менял».

Типы, которые реально нужны: `feat`, `fix`, `refactor`, `perf`, `style`,
`test`, `docs`, `chore`.

Язык сообщений: в истории смешаны русский и английский
(`fix: учёт вышедших серий` рядом с `refactor: migrate public frontend assets`).
Выбрать один и держаться. Для портфолио, которое будут смотреть чужие
люди — английский.

## Раскладка текущего рабочего дерева

В работе 21 файл незакоммиченных изменений. Складывается минимум в шесть
коммитов:

```
1  chore(deps): add inertia and vue
   composer.json composer.lock package.json package-lock.json

2  feat(inertia): bootstrap inertia runtime
   app/Http/Middleware/HandleInertiaRequests.php
   config/inertia.php
   app/Http/Kernel.php
   resources/views/app.blade.php
   resources/js/app.js
   vite.config.js

3  feat(home): render main page through inertia
   resources/js/Pages/ resources/js/Layouts/ resources/js/Components/
   app/Http/Controllers/MainController.php
   resources/views/pages/dcote-main.blade.php
   resources/js/main.js
   D resources/js/pages/dcote-main.js

4  style(home): replace custom scrollbar with native one
   resources/css/pages/dcote-main.css  (только часть про скроллбар, через add -p)
   docs/native-scrollbar.md

5  fix(header): <описать по факту диффа>
   resources/css/header.css

6  refactor(ranobe): <описать по факту диффа>
   app/Helpers/MarkdownRanobeHelper.php
```

Обрати внимание на шестой. `MarkdownRanobeHelper` к миграции на Inertia
отношения не имеет — это ровно тот отвлечённый тангенс, который внутри
коммита «feat: migrate to inertia» растворился бы бесследно. Отдельным
коммитом он читается.

Коммиты 2 и 3 проверять отдельно (`npm run build` плюс открыть сайт): если
Inertia сломается, нужно знать, на каком из двух шагов.

## Ветки

Текущее состояние: `main`, `production`, `comments`, `rating-widget`.
Из них `comments` содержит работу по Inertia, а не по комментариям.

Схема, которая подойдёт для solo с напарником:

- `production` — то, что задеплоено. Пушить только через merge из `main`.
- `main` — интеграционная. Тесты должны быть зелёными.
- `feat/*`, `fix/*` — рабочие, живут дни, не недели.

Правило именования: ветка называется по содержимому, и если содержимое
изменилось — переименовать сразу, а не «потом разберусь».

## PR даже в одиночку

В истории один PR (`#1`), остальное — прямые коммиты. Для solo это кажется
избыточным, но PR даёт две вещи, которых иначе нет: CI-прогон до мержа и
описание изменения, которое переживёт твою память.

Минимальная привычка: любая ветка длиннее одного дня уходит в PR, даже если
мержишь сам через пять минут.

## Что даёт больше всего пользы за меньше всего усилий

1. `git add -p` вместо `git add .` — решает 80% проблемы разделения.
2. `NOTES.md` для отвлечений — решает причину, а не следствие.
3. Тесты в CI до деплоя — снимает главный структурный минус профиля.
