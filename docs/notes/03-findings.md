# Найденное: баги, недочёты, идеи

Список составлен по чтению кода, а не по логам. Где важно — указано, чем
подтверждено и что ещё надо проверить руками.

Приоритеты:

- **P0** — ломается у живых юзеров прямо сейчас
- **P1** — скрытая порча данных или безопасность
- **P2** — упрётся при росте
- **P3** — качество кода, удобство поддержки

## P1. Нет индексов под фактические запросы

Ни в одной миграции нет ни одного явного индекса. `$table->morphs()` создаёт
составной индекс `(type, id)` — это есть у `ratings` и `populars`.

Чего не хватает:

`anime_episodes` — запросы всегда идут по `(season_id, episode_number)`:
`AnimeController.php:60,90,144,172`. `foreignId` даёт индекс только на
`season_id`. Нужен составной, он же обеспечит уникальность, которую сейчас
сторожит PHP-код (`GuardsNaturalKeyUniqueness`):

```php
$table->unique(['season_id', 'episode_number']);
```

`ranobe_chapters` — то же самое по `(ranobe_volume_id, chapter_number)`.

`ranobe_volumes` — `(ranobe_year_id, volume_number)`.

`anime_seasons.season_number` — используется как ключ во всех роутах,
уникальный по смыслу, индекса нет.

Про уникальность отдельно: сейчас она проверяется запросом `SELECT` перед
сохранением. Между проверкой и вставкой есть окно — два одновременных
сохранения в Filament пройдут оба. Уникальный индекс в БД закрывает это
на уровне движка. Трейт остаётся для человекочитаемого сообщения, но
становится удобством, а не гарантией.

Порядок: сначала проверить, нет ли уже дублей (иначе миграция упадёт), потом
добавлять.

```sql
SELECT season_id, episode_number, COUNT(*) c
FROM anime_episodes GROUP BY 1,2 HAVING c > 1;
```

## P2. Коррелированные подзапросы в списке сезонов

`AnimeController.php:22-41` — на каждый сезон выполняется подзапрос с
`whereIn` по вложенному подзапросу, и таких блоков два (avg и count).
Плюс то же самое трижды в `RanobeController.php:39-56`.

Сейчас сезонов единицы, и это незаметно. При росте рейтингов запрос
деградирует нелинейно, потому что внутренний `whereIn (SELECT id FROM
anime_episodes WHERE season_id = ...)` MySQL не всегда оптимизирует в join.

Замер до оптимизации (обязательно, иначе непонятно, что улучшаешь):

```sql
EXPLAIN ANALYZE <запрос из лога>;
```

Варианты решения по возрастанию сложности:

1. Заменить подзапросы на `withAvg`/`withCount` через связь
   `hasManyThrough` — Eloquent сгенерирует join.
2. Кэшировать агрегаты на 5-10 минут (`Cache::remember`). Рейтинги не
   требуют мгновенной точности в списке.
3. Денормализовать: `anime_seasons.avg_rating` + `ratings_count`,
   пересчёт при изменении рейтинга. Самое быстрое чтение, самая дорогая
   поддержка. Делать только если 1 и 2 не хватило.

Начинай с 1, замерь, дальше по результату.

## P2. Общий rate limit на голосовании

`routes/api.php:11-14` — рейтинги под `auth:sanctum` и общим `throttle:api`
(60 запросов/минуту из `Kernel.php:44`).

Один авторизованный юзер может отправить 60 голосов в минуту. Поскольку это
`updateOrCreate` по уникальному ключу, накрутить средний балл не получится,
но можно устроить лишнюю нагрузку на БД.

```php
Route::middleware(['auth:sanctum', 'throttle:10,1'])->group(function () {
    Route::post('/ratings', [RatingController::class, 'store']);
    Route::delete('/ratings', [RatingController::class, 'destroy']);
});
```

Для комментариев это станет обязательным, а не желательным — там лимит
защищает от спама, а не только от нагрузки.

## P2. `CACHE_DRIVER=file` при синхронизаторе на блокировке

`.env` и README (prod-секция) задают `CACHE_DRIVER=file`, `SESSION_DRIVER=file`.

`PublicationStateSynchronizer` использует `Cache::add()` как распределённую
блокировку. На файловом драйвере `add` не атомарен между процессами:
php-fpm с несколькими воркерами может пропустить два одновременных запроса
внутрь. Последствие мягкое (два одинаковых идемпотентных UPDATE), но сам
паттерн ненадёжен.

Отдельно про сессии на файлах: при 180 одновременных зрителях это тысячи
файлов в `storage/framework/sessions` и линейный рост стоимости их чтения.

Redis решает оба вопроса и стоит один сервис в compose:

```yaml
redis:
    image: redis:7-alpine
    restart: unless-stopped
    networks: [app]
```

```env
CACHE_DRIVER=redis
SESSION_DRIVER=redis
```

Это же нужно для очередей, когда появятся уведомления о комментариях
(`QUEUE_CONNECTION=sync` сейчас означает, что всё выполняется в
HTTP-запросе).

## P2. Sitemap генерируется по расписанию, которое не запускается

`Console/Kernel.php:18-20` — `sitemap:generate` ежедневно в 03:00. Но
`schedule:run` нигде не вызывается: в `docker-compose.prod.yml` нет ни cron,
ни supervisor-программы для него, а `deploy.yml` его не ставит.

Значит `public/sitemap.xml` обновляется только вручную. Для проекта, живущего
на SEO, это прямая потеря: новые главы и серии не попадают в карту.

Проверить дату файла на сервере:

```bash
ls -la public/sitemap.xml
```

Решение — то же, что закрывает и вопрос с синхронизатором: одна cron-строка
на хосте.

```
* * * * * cd /var/www/dcote.net && docker compose -f docker-compose.prod.yml exec -T app php artisan schedule:run >> /dev/null 2>&1
```

## P3. Дублирование в MainController

`MainController.php:27-53` — два идентичных блока для `spoilers = 0` и
`spoilers = 1`, различающихся одним значением. 27 строк, из которых 13 —
копия.

Сворачивается в метод или скоуп на модели:

```php
// ClassesTop
public static function rankedByPoints(bool $spoilers): Collection
{
    $items = static::where('spoilers', $spoilers)
        ->orderByDesc('class_points')
        ->get();

    $max = $items->first()?->class_points ?? 0;

    return $items->each(fn ($class) => $class->percent = $max > 0
        ? min(100, round($class->class_points / $max * 100, 2))
        : 0);
}
```

Заодно `percent` перестанет быть полем, которое приклеивается к модели
в контроллере — это скрытый контракт с фронтом, который сейчас нигде не
задокументирован.

## Идеи развития (не баги)

### Ближайшее по ценности

**Профиль пользователя.** Понадобится для комментариев всё равно. Закрывает
P0 с `/account`. Содержимое: аватар, ник, роль, список оценок, список
комментариев.

**Избранное.** Морф-таблица `favorites` с той же схемой, что `ratings`.
Хорошее упражнение, чтобы сделать морф-связь своими руками с нуля — и снять
пункт «морфы делал не я».

**История просмотра.** Сейчас прогресс серий хранится в localStorage
(`docs/frontend.md` про `data-episode-number`). Перенос на сервер для
авторизованных даёт синхронизацию между устройствами. Ощутимая для юзеров
фича при небольшой работе.

### Инфраструктура

**Health-check эндпоинт.** `/up` с проверкой БД и кэша. Нужен для мониторинга
и для `depends_on: condition: service_healthy` у `app`.

**Мониторинг ошибок.** Sentry в бесплатном тарифе. Сейчас единственный способ
узнать о 500 — залезть в `storage/logs` руками. Мёртвые роуты из P0 — прямое
доказательство, что этого способа недостаточно.

**Бэкапы БД.** В compose есть `mysql-data` volume, но нет ни одного скрипта
бэкапа. С учётом истории с захватом хостинга это удивительное упущение.
`spatie/laravel-backup` + выгрузка в тот же R2, где уже лежат картинки.

Это, кстати, сильный пункт для рассказа на интервью: «после инцидента я
настроил автоматические бэкапы с выгрузкой в отдельное хранилище».

**Zero-downtime деплой.** Сейчас `deploy.yml` делает `build` и `up -d` —
между остановкой и запуском контейнера сайт недоступен. Не критично, но
`--no-deps` + пересборка одного сервиса сокращает окно.

### SEO (твой главный актив)

**Структурированные данные.** JSON-LD разметка `TVSeries`/`TVEpisode` для
аниме и `Book` для томов. Даёт расширенные сниппеты в выдаче. Дешёвая работа
с прямым влиянием на CTR.

**Open Graph.** Проверить, есть ли на страницах серий и глав. Влияет на то,
как ссылки выглядят в Telegram — а у проекта есть канал.

**Скорость.** `fetchpriority`, `decoding="async"`, WebP уже есть — видно,
что Lighthouse смотрел. Следующий шаг: замерить LCP на мобильных через
PageSpeed Insights и записать цифру в README. Конкретное число там работает
лучше слов.
