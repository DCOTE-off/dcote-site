# Порядок работ

Изначальный план: всё на Vue → SPA → комментарии.
Предлагаемый: разгрести → рассказать → комментарии на Vue → миграция точечно
→ SSR как условие для SPA.

Разница в одном принципе: **не «сначала переписать, потом делать», а «делать
новое сразу на новом стеке»**. Тогда миграция происходит по ходу, а проект
в любой момент остаётся живым и продаваемым.

---

## Почему не «сначала полный SPA»

**SEO — основной актив проекта.** 100k показов, третьи строчки, 5k кликов.
Приносят их страницы глав ранобэ и серий аниме. Inertia без SSR отдаёт пустой
`<div id="app">` и рендерит контент джаваскриптом. Google это переваривает
более-менее, Яндекс — заметно хуже и непредсказуемее. План в текущем виде
означает переписать на клиентский рендеринг ровно те страницы, которые кормят
проект, и узнать результат через 2-3 месяца по просевшим позициям. Откат будет
дороже, чем сама миграция.

**Масштаб.** 14 Blade-страниц против одной Vue. Полная миграция — это месяцы,
в течение которых не выходит ни одной новой фичи. Проект с живыми юзерами
не должен так долго стоять.

**Ценность для найма.** Комментарии — разговор на сорок минут: схема,
вложенность, N+1, модерация, спам, права. «Перенёс Blade на Vue» — разговор
на пять минут, и он про инструмент, а не про инженерное мышление.

Отдельно: комментарии на Vue как остров внутри Blade-страницы дают ровно ту же
практику Vue, что и миграция, но без риска для SEO. Учишься на новой фиче,
а не на переписывании работающего.

## Фаза 1. Позиционирование (один вечер)

Самая высокая отдача на час работы во всём списке. Код уже есть, этого — нет.

```
[ ] Переписать первый экран README: цифры вместо описания
[ ] docs/incidents.md — инцидент с хостингом
[ ] docs/infrastructure.md — три сервиса и почему разнесены
[ ] Актуализировать или удалить docs/frontend.md (он врёт, см. 03-findings.md)
```

**README.** Сейчас после бейджей идёт «Фан-сайт ранобэ...». Первые 15 строк
должны отвечать на «зачем этого человека брать», а не «как запустить докер».
Туда: показы и клики в месяц, позиции по ключевым запросам, сколько
одновременных зрителей держит видео, сколько живёт проект. Инструкции по
локальному запуску — ниже или в `docs/`. Читают первый экран; дальше — только
если зацепило.

**incidents.md.** Формат: что случилось, как обнаружил, радиус поражения, что
сделал в первые часы, как переехал, что изменил после, чему научился.

Про радиус поражения спросят обязательно — заготовь ответ по пунктам:
`APP_KEY`, креды БД, SSH-ключи, сессии, ключи Turnstile, доступы к R2. Что
ротировал, что нет и почему.

Правильная рамка: «инцидент был на стороне провайдера, я обнаружил, оценил
радиус, переехал, вот что изменил». Неправильная: «нас взломали». Первое
звучит как инженер, второе — как жертва.

Постмортем — язык, на котором говорят синьоры. Сам факт, что ты его написал,
работает сильнее содержания.

**infrastructure.md.** `docs/metrics-contract.md` отвечает на «как устроен
контракт», но не на «почему три отдельных сервиса, а не монолит». Ответ у тебя
есть — он нигде не записан. Схема из трёх блоков плюс абзац обоснования.


### Решения до кода

**Вложенность.** Плоский список — проще всего, но юзеры начнут писать «@ник»
руками. `parent_id` с одним уровнем — оптимум для фан-сайта, дерево грузится
двумя запросами. Полное дерево произвольной глубины требует materialized path
или nested set, иначе N+1 гарантирован — для твоего масштаба оверинжиниринг.

Рекомендация: `parent_id`, один уровень. Ответ на ответ прикрепляется к тому
же родителю.

**Удалённые с ответами.** Физическое удаление ломает контекст ответов.
Стандартное решение — soft delete плюс «комментарий удалён» на фронте.

**Морф или прямая связь.** Комментарии нужны к сериям, томам, главам — морф.
Это шанс сделать морф-связь с нуля своими руками. Механика и грабли —
в `01-unknown-code.md`. Важно: **не повторить баг с двойным алиасом**. Один
класс — один алиас.

### Схема

```php
Schema::create('comments', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->morphs('commentable');
    $table->foreignId('parent_id')->nullable()
        ->constrained('comments')->cascadeOnDelete();
    $table->text('body');
    $table->timestamps();
    $table->softDeletes();

    $table->index(['commentable_type', 'commentable_id', 'created_at']);
});
```

Составной индекс с `created_at` в конце — потому что запрос всегда «комментарии
к этой сущности, отсортированные по дате». `morphs()` даёт индекс `(type, id)`,
но не покрывает сортировку.

### Что спросят по этой фиче

Это же и чек-лист качества:

- Как грузишь дерево без N+1?
- Что при удалении юзера? (`cascadeOnDelete` снесёт его комментарии — это
  желаемое поведение?)
- Как защищаешь от XSS при выводе? (`SafeDescriptionHelper` есть, но для
  пользовательского ввода нужен более строгий подход)
- Как считаешь счётчик комментариев в списках без запроса на каждую сущность?
- Что мешает боту запостить 1000 комментариев?
- Видно ли, что комментарий отредактирован?
- Пагинация: offset или cursor?

Последний с подвохом: для комментариев лучше cursor, потому что при добавлении
новых записей offset «съезжает» и юзер видит дубли. Laravel умеет
`cursorPaginate()`.

## Фаза 3. Миграция на Vue по ценности

Не «все страницы по порядку», а «те, где Vue даёт выигрыш».

**Переносить.** `reading-settings` — 294 строки JS с состоянием и localStorage,
во Vue станет вдвое короче. Лучший первый кандидат: максимальный выигрыш,
нулевой SEO-риск (не индексируется). `anime/season` — сортировка, FLIP,
сворачивание; императивная логика становится декларативной, но это SEO-страница,
поэтому после разбирательства с SSR.

**Не переносить.** `rules`, `privacy-policy`, `about-school`, `about-project`.
Статика. Blade для статики — правильный инструмент, а не устаревший.

**Спорные, по замерам.** `ranobe/chapter`, `anime/index`, `ranobe/index` —
основной SEO-трафик.

**Обязательно:** таблица в README «страница → Blade или Inertia → статус».
Пока живёт гибрид, это самый нужный документ в проекте. Без него через месяц
сам не помнишь, где что, и появляются баги на стыке.

Задачи на время гибрида: в `SiteHeader.vue` смешаны `<Link>` (строка 26)
и обычные `<a>` (строки 33-38) — это правильно, но нужен комментарий
с объяснением, иначе кто-то «поправит» на единообразие и сломает переходы.
Инлайн-стили в `SiteHeader.vue:66,78` — в классы или проп `variant`, сейчас
цвет кнопки нельзя изменить в одном месте.

## Фаза 4. SPA — только с SSR

Условие входа:

```
[ ] inertia:start-ssr работает локально
[ ] Сравнена выдача для бота до и после на одной странице
[ ] Замерены позиции в Яндексе по 3-5 запросам ДО перехода
```

Проверка того, что видит поисковик:

```bash
curl -s https://dcote.net/ranobe/2016/1 | grep -c "текст из главы"
```

Ноль — значит контента в HTML нет и Яндексу нечего индексировать.

SSR добавляет отдельный Node-процесс в прод: плюс сервис в compose, плюс
мониторинг, плюс новый режим отказа. Осознанная цена, а не «включить флаг».

Честный вариант: возможно, полный SPA этому проекту не нужен вообще. Inertia
уже даёт SPA-навигацию там, где она полезна, а статичные страницы от Blade
ничего не теряют. Решение «оставить гибрид и задокументировать почему» — тоже
инженерное решение, и на интервью защищается лучше, чем «переписал всё, потому
что хотел освоить фреймворк».
